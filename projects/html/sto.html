기술적 선택 근거

프로젝트는 부동산 STO 거래 플랫폼으로, 일반적인 CRUD 서비스뿐 아니라 주문 매칭, 실시간 시세 반영, 배당금 지급 자동화처럼 성격이 다른 기능들이 함께 존재했습니다.
따라서 모든 기능을 하나의 모놀리식 서버에 넣기보다 역할에 따라 Main 서버, Match 서버, Batch 서버로 분리했습니다.
Main 서버는 회원, 자산, 주문, 계좌, 관리자 기능 등 주요 API 요청을 처리하고, Match 서버는 주문 요청을 받아 가격-시간 우선순위 기반으로 체결을 수행하도록 구성했습니다. Batch 서버는 배당금 지급, 토큰 상장 상태 변경, 블록체인 기록 처리처럼 주기적으로 실행되는 작업을 담당하도록 분리했습니다.
이를 통해 주문 체결 로직이나 배치 작업이 일반 API 요청 처리에 직접적인 영향을 주지 않도록 했고, 추후 거래량 증가나 배치 작업 증가에 따라 서버별로 독립적인 확장과 관리가 가능하도록 설계했습니다.

서비스 특성상 호가창, 체결 내역, 캔들 차트, 미체결 주문, 관리자 실시간 대시보드 등 실시간으로 갱신되어야 하는 화면이 많았습니다.
단순 HTTP polling 방식은 주기적으로 불필요한 요청이 발생하고, 체결 직후 즉시 반영되어야 하는 거래 서비스의 특성과 맞지 않는다고 판단했습니다. 그래서 WebSocket 기반의 실시간 통신을 사용했고, 구독 기반 메시지 처리를 명확하게 관리하기 위해 STOMP를 선택했습니다.
이를 통해 클라이언트는 /topic/orderBook, /topic/trades, /topic/candle과 같은 채널을 구독하고, 서버는 주문 체결이나 시세 변경이 발생했을 때 필요한 화면에만 실시간 이벤트를 전달할 수 있도록 구성했습니다.

서버가 Main 서버와 Match 서버로 분리되어 있기 때문에, Match 서버에서 주문이 체결되었을 때 그 결과를 Main 서버와 프론트엔드 실시간 화면에 전달할 수 있는 메시지 전달 구조가 필요했습니다.
이를 위해 Redis Pub/Sub을 도입했습니다. Match 서버는 체결 결과와 호가 변경 이벤트를 Redis 채널로 publish하고, Main 서버는 이를 subscribe하여 WebSocket/STOMP를 통해 클라이언트에게 전달하도록 구성했습니다.
이 구조를 통해 서버 간 결합도를 낮추면서도 체결 결과, 호가창, 캔들 차트, 관리자 대시보드가 실시간으로 갱신되도록 구현했습니다.

Docker Compose 기반으로 Main·Match·Batch 서버와 PostgreSQL, Redis, Nginx를 컨테이너 환경으로 구성해 배포 환경을 통합 관리했습니다.

React 기반 CSR 구조에 맞춰 JWT 기반 Stateless 인증 방식을 적용했습니다.

QueryDSL 기반 동적 쿼리를 적용해 거래량·거래대금·가격 변동률 등 다양한 정렬 조건을 확장 가능하게 구현했습니다.

Swagger를 활용해 API 명세를 자동화하고 프론트엔드와 협업 효율을 높였습니다.

블록체인 설계

오프체인(DB)·온체인(블록체인) 하이브리드 구조를 적용해, 주문 매칭·정산·잔고 반영은 DB에서 우선 처리하고 체결 결과만 블록체인에 기록하도록 설계했습니다. 이를 통해 블록체인의 느린 처리 속도와 높은 비용 문제를 보완하면서도, 체결 이력의 무결성과 추적 가능성을 확보했습니다.

Ethereum Sepolia 테스트넷 환경에서 ERC-20 표준 기반의 STO 토큰 컨트랙트를 배포했으며, 체결 발생 시 메인 서버가 DB 정산을 완료한 뒤 Outbox Queue에 거래 정보를 적재하도록 구성했습니다. 이후 Batch 서버가 10초 주기로 Queue를 읽어 스마트컨트랙트의 recordTrade()를 호출해 거래 이벤트를 기록하고, 트랜잭션 해시·블록번호·가스 사용량 등을 저장해 온체인 기록 상태를 관리했습니다. 또한 재시도 및 상태 동기화 로직을 구현해 블록체인 기록 안정성을 높이고, 관리자 대시보드에서 실시간 정산 및 온체인 기록 현황을 조회할 수 있도록 구성했습니다.

문제와 해결

1. 실시간 캔들 차트(Live Candle) 동기화 아키텍처 설계

토큰 상세 페이지의 핵심 기능인 캔들 차트를 구현하며, '현재 진행 중인 시간대'의 실시간 데이터 동기화 문제에 직면했습니다.
예를 들어 사용자가 '2026년 1월 10일 오전 10시 23분 40초'에 상세 페이지에 접근했다고 가정할 때, 22분, 21분, 20분 등 과거 완성된 캔들 차트는 데이터베이스에서 조회하면 됩니다.
하지만 '23분'대(접속한 시간대)의 캔들 데이터는 23분이 완전히 지나고 24분 00초가 되어야 DB에 저장됩니다. 그렇다면 '23분 40초'에 접속한 사용자는 아직 DB에 없는 '23분 00초 ~ 23분 40초' 사이의 캔들 차트 데이터를 어떻게 조회해야 하는지가 핵심 난제였습니다.
이에 현업 멘토님과의 심도 있는 자문과 논의를 거쳐, 23분 00초 ~ 24분 00초 동안 체결되는 데이터를 실시간으로 보관하는 메모리 자료구조인 CandleLiveManager(ConcurrentHashMap 기반, Key = 토큰 ID, Value = LiveCandleDTO)를 설계했습니다.
이 구조를 통해 사용자가 '10시 23분 40초'에 접속하면 22분 이전의 과거 데이터는 DB에서 조회하고, 23분대의 실시간 라이브 데이터는 CandleLiveManager에서 Key 값으로 즉시 조회해 조합하는 하이브리드 조회 구조를 완성할 수 있었습니다.
이 과정을 통해 낯선 도메인의 아키텍처 한계에 부딪혔을 때, 스스로 문제를 명확히 정리한 뒤 시니어에게 자문을 구하는 커뮤니케이션과 문제 해결 방식의 중요성을 깊이 체감했습니다.

2. QueryDSL 기반 토큰 목록 정렬 확장성 개선

메인 페이지 토큰 목록은 기본 조회 외에 거래대금순, 거래량순 정렬 기능이 필요했습니다.
초기에는 각 정렬마다 별도 API를 분리하는 방식을 고려했으나, 향후 등락률순, 시가총액순 등 조건이 추가될 경우를 대비해 selectType 파라미터 기반의 동적 조회 구조로 설계했습니다.
QueryDSL을 활용하여 파라미터에 따라 집계 기준을 동적으로 변경하고 DB 레벨에서 정렬과 페이징을 처리하도록 구현함으로써, 무분별한 중복 API 생성을 방지하고 메인 페이지 조회 로직의 확장성을 크게 높였습니다.
