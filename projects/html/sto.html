담당 역할

백엔드 개발 및 인프라 구축 담당

Spring Boot 기반 백엔드 개발 및 멀티 서버 아키텍쳐 설계

  • ERD 및 API 공동 설계
  • 예외 계층화 (ErrorCode), 컨트롤러 예외 처리 (Rest Controller Advice) 등 팀 전용 예외 설계, 구현
  • 팀 전용 코드 컨벤션 수립 (Naming Convention)
  • 멀티 서버 아키텍처 설계 [main 서버, match 서버, batch 서버]
  • 백엔드 개발 - STO 메인 페이지(STO 전체 리스트 구현), 상세 페이지 (캔들 차트, 호가창, 체결 완료 내역 등을 실시간으로 구현)
  • 금융 관련 중요 정보(호가/주문, 주문 체결 결과) 이중 저장을 위한 백업 테이블 설계 및 구현

팀 전용 코드 컨벤션

  • 공통 필드 관리: 생성일, 수정일이 모두 필요한 경우 BaseEntity를 상속, 생성일만 필요한 엔티티는 클래스 내부에 직접 정의
  • 엔티티 연관관계: 가급적 단방향으로 설계하며, 양방향 필요 시 팀원과 사전 협의 후 개발
  • 메서드 네이밍: 계층별 역할에 맞춰 분리 (Repository는 JPA 스펙, Service는 비즈니스 로직 중심)
  • 요청 데이터 검증: 클라이언트 요청(Request DTO) 데이터는 철저하게 Validation 검증 수행
  • API 응답 타입 통일: REST API 응답은 일관되게 ResponseEntity 타입으로 반환 처리
  • 엔티티 수정 방식: 단일 업데이트 시 save() 대신 JPA 변경 감지(Dirty Checking) 활용

기술적 선택 근거

프로젝트는 부동산 STO 거래 플랫폼으로, 일반적인 CRUD 서비스뿐 아니라 주문 매칭, 실시간 시세 반영, 배당금 지급 자동화처럼 성격이 다른 기능들이 함께 존재했습니다.
따라서 모든 기능을 하나의 모놀리식 서버에 넣기보다 역할에 따라 Main 서버, Match 서버, Batch 서버로 분리했습니다.
Main 서버는 회원, 자산, 주문, 계좌, 관리자 기능 등 주요 API 요청을 처리하고, Match 서버는 주문 요청을 받아 가격-시간 우선순위 기반으로 체결을 수행하도록 구성했습니다. Batch 서버는 배당금 지급, 토큰 상장 상태 변경, 블록체인 기록 처리처럼 주기적으로 실행되는 작업을 담당하도록 분리했습니다.
이를 통해 주문 체결 로직이나 배치 작업이 일반 API 요청 처리에 직접적인 영향을 주지 않도록 했고, 추후 거래량 증가나 배치 작업 증가에 따라 서버별로 독립적인 확장과 관리가 가능하도록 설계했습니다.

서비스 특성상 호가창, 체결 내역, 캔들 차트, 미체결 주문, 관리자 실시간 대시보드 등 실시간으로 갱신되어야 하는 화면이 많았습니다.
단순 HTTP polling 방식은 주기적으로 불필요한 요청이 발생하고, 체결 직후 즉시 반영되어야 하는 거래 서비스의 특성과 맞지 않는다고 판단했습니다. 그래서 WebSocket 기반의 실시간 통신을 사용했고, 구독 기반 메시지 처리를 명확하게 관리하기 위해 STOMP를 선택했습니다.
이를 통해 클라이언트는 /topic/orderBook, /topic/trades, /topic/candle과 같은 채널을 구독하고, 서버는 주문 체결이나 시세 변경이 발생했을 때 필요한 화면에만 실시간 이벤트를 전달할 수 있도록 구성했습니다.

서버가 Main 서버와 Match 서버로 분리되어 있기 때문에, Match 서버에서 주문이 체결되었을 때 그 결과를 Main 서버와 프론트엔드 실시간 화면에 전달할 수 있는 메시지 전달 구조가 필요했습니다.
이를 위해 Redis Pub/Sub을 도입했습니다. Match 서버는 체결 결과와 호가 변경 이벤트를 Redis 채널로 publish하고, Main 서버는 이를 subscribe하여 WebSocket/STOMP를 통해 클라이언트에게 전달하도록 구성했습니다.
이 구조를 통해 서버 간 결합도를 낮추면서도 체결 결과, 호가창, 캔들 차트, 관리자 대시보드가 실시간으로 갱신되도록 구현했습니다.

프로젝트는 신한 DS 내부망의 제한된 배포 환경에서 운영되었고, 팀별로 단일 서버를 제공받는 조건이 있었습니다. 하나의 서버 안에서 Main 서버, Match 서버, Batch 서버, PostgreSQL, Redis, Nginx를 함께 실행해야 했기 때문에 Docker를 사용했습니다.
각 서비스를 컨테이너 단위로 분리하여 실행 환경을 독립적으로 관리했고, 로컬 개발 환경과 배포 환경의 차이를 줄일 수 있도록 구성했습니다. 또한 Docker Compose를 통해 여러 서비스를 한 번에 실행하고, 서비스 간 네트워크와 환경변수를 일관되게 관리할 수 있도록 했습니다.

프론트엔드는 React + Vite 기반의 CSR 구조로 구현했습니다. 서버가 화면 렌더링을 담당하지 않고 API 중심으로 동작하기 때문에, 서버 세션에 인증 상태를 저장하는 방식보다 stateless한 JWT 인증 방식이 적합하다고 판단했습니다.
JWT를 사용해 로그인 이후 클라이언트가 access token을 보관하고, API 요청 시 Authorization 헤더로 전달하도록 구성했습니다. 이를 통해 Main 서버는 세션 저장소에 의존하지 않고 요청 단위로 인증을 검증할 수 있었고, 향후 서버 확장 시에도 인증 상태 공유에 대한 부담을 줄일 수 있었습니다.

메인 페이지와 관리자 페이지에서는 토큰 목록을 단순 조회하는 것뿐 아니라 거래대금순, 거래량순, 가격 변동률, 키워드 검색 등 다양한 조건에 따라 동적으로 조회해야 했습니다.
Spring Data JPA의 기본 메서드 쿼리만으로는 조건 조합이 많아질수록 메서드가 과도하게 늘어나고, 문자열 기반 JPQL은 컴파일 시점에 오류를 잡기 어렵다고 판단했습니다. 그래서 QueryDSL을 사용해 타입 안전한 방식으로 동적 쿼리를 구성했습니다.
이를 통해 검색 조건과 정렬 조건을 조합하면서도 쿼리 로직을 명확하게 유지할 수 있었고, 조회 기능의 확장성과 유지보수성을 높일 수 있었습니다.

프론트엔드와 백엔드가 분리된 구조였기 때문에 API 명세를 명확하게 공유하는 것이 중요했습니다. 특히 주문, 자산 등록, 관리자 기능처럼 요청/응답 DTO가 복잡한 API가 많아 구두 공유나 별도 문서만으로는 커뮤니케이션 비용이 커질 수 있다고 판단했습니다.
Swagger를 도입해 백엔드 API 명세를 자동 문서화했고, 프론트엔드 개발자가 엔드포인트, 요청 파라미터, 응답 구조를 직접 확인할 수 있도록 했습니다. 이를 통해 API 변경 시 소통 비용을 줄이고, 프론트-백엔드 간 연동 과정에서 발생하는 오해를 줄일 수 있었습니다.

성능 개선

1. 실시간 캔들 차트(Live Candle) 동기화 아키텍처 설계

토큰 상세 페이지의 핵심 기능인 캔들 차트를 구현하며, '현재 진행 중인 시간대'의 실시간 데이터 동기화 문제에 직면했습니다.
예를 들어 사용자가 '2026년 1월 10일 오전 10시 23분 40초'에 상세 페이지에 접근했다고 가정할 때, 22분, 21분, 20분 등 과거 완성된 캔들 차트는 데이터베이스에서 조회하면 됩니다.
하지만 '23분'대(접속한 시간대)의 캔들 데이터는 23분이 완전히 지나고 24분 00초가 되어야 DB에 저장됩니다. 그렇다면 '23분 40초'에 접속한 사용자는 아직 DB에 없는 '23분 00초 ~ 23분 40초' 사이의 캔들 차트 데이터를 어떻게 조회해야 하는지가 핵심 난제였습니다.
이에 현업 멘토님과의 심도 있는 자문과 논의를 거쳐, 23분 00초 ~ 24분 00초 동안 체결되는 데이터를 실시간으로 보관하는 메모리 자료구조인 CandleLiveManager(ConcurrentHashMap 기반, Key = 토큰 ID, Value = LiveCandleDTO)를 설계했습니다.
이 구조를 통해 사용자가 '10시 23분 40초'에 접속하면 22분 이전의 과거 데이터는 DB에서 조회하고, 23분대의 실시간 라이브 데이터는 CandleLiveManager에서 Key 값으로 즉시 조회해 조합하는 하이브리드 조회 구조를 완성할 수 있었습니다.
이 과정을 통해 낯선 도메인의 아키텍처 한계에 부딪혔을 때, 스스로 문제를 명확히 정리한 뒤 시니어에게 자문을 구하는 커뮤니케이션과 문제 해결 방식의 중요성을 깊이 체감했습니다.

2. QueryDSL 기반 토큰 목록 정렬 확장성 개선

메인 페이지 토큰 목록은 기본 조회 외에 거래대금순, 거래량순 정렬 기능이 필요했습니다.
초기에는 각 정렬마다 별도 API를 분리하는 방식을 고려했으나, 향후 등락률순, 시가총액순 등 조건이 추가될 경우를 대비해 selectType 파라미터 기반의 동적 조회 구조로 설계했습니다.
QueryDSL을 활용하여 파라미터에 따라 집계 기준을 동적으로 변경하고 DB 레벨에서 정렬과 페이징을 처리하도록 구현함으로써, 무분별한 중복 API 생성을 방지하고 메인 페이지 조회 로직의 확장성을 크게 높였습니다.

회고 및 배운 점

동기식 서버 통신의 한계와 비동기 아키텍처

Main 서버와 Match 서버 간 HTTP 동기 호출 구조에서 발생할 수 있는 처리 지연 및 장애 전파 문제를 경험했습니다.
이를 통해 대규모 트래픽 처리가 중요한 금융 서비스에는 메시지 큐(Kafka, RabbitMQ)를 활용한 비동기 통신 및 이벤트 기반 아키텍처 도입이 필수적임을 배웠습니다.

데이터 파이프라인과 관심사 분리

핵심 비즈니스 로직과 데이터 백업/적재 로직이 강하게 결합된 구조의 한계를 느꼈습니다.
향후 Kafka Connect와 같은 이벤트를 활용해 데이터 적재 로직을 분리함으로써, 애플리케이션은 거래 로직에만 집중하고 데이터 파이프라인은 독립적으로 운영되는 구조의 필요성을 학습했습니다.

금융 도메인 이해와 구현의 차이

전공 지식이 있음에도 실시간 캔들 차트 로직 등을 구현하며 사용자로서 아는 것과 개발자로서 구현하는 것의 깊이 차이를 체감했습니다.
금융 서비스 개발에서는 기능 구현 능력만큼이나 도메인 개념에 대한 정확한 분석과 이해가 선행되어야 한다는 점을 느꼈습니다.

초기 설계의 중요성 체감

평소 계획적인 성격으로 일정이 지연되는 것을 경계하는 편입니다. 프로젝트 초반, 난이도 높은 ERD 설계로 일정이 늦어지자 팀원들에게 '개발을 병행하며 수정하자'고 제안하며 팀원들과 갈등을 겪기도 했습니다.
하지만 막상 개발에 착수해보니, 탄탄한 설계 덕분에 엔티티 구현과 로직 개발 시 구조적 고민 없이 속도를 낼 수 있었습니다. 무조건 빠른 시작보다 '제대로 된 설계'가 최종 개발 시간을 단축시킨다는 진정한 의미를 체감한 계기가 되었습니다.
