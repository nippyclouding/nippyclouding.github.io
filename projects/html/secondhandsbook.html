중고책 거래 파이프라인

중고책 거래글 등록 → 구매자와 판매자 간 1:1 채팅 → 안전 결제 → 판매 대금 정산

안전 결제

safe_payment_st = NONE, PENDING, COMPLETED

판매 대금 정산

settlement_st = NONE, READY, REQUESTED, COMPLETED

정산 1 (NONE → READY)
정산 2 (READY → REQUESTED)
정산 3 (REQUESTED → COMPLETED)

문제와 해결 : 도메인 특성에 따른 동시성 제어 전략 분리

"같은 동시성 문제라도 결제 요청은 '짧은 선점 경쟁'이라 조건부 UPDATE로 풀고, 정산 신청은 '검증과 생성이 묶인 금융 트랜잭션'이라 FOR UPDATE로 풀었습니다. 락을 일괄 적용하지 않고, 업무 흐름의 위험도에 따라 동시성 제어 전략을 분리한 점이 차별점입니다."

1. 안전결제는 락보다 상태 전이 게이트로 해결 (조건부 UPDATE)

안전결제 요청 과정에서는 여러 구매자가 동시에 결제를 시도하는 짧고 빈번한 경쟁이 발생할 수 있습니다. 이를 해결하기 위해 병목을 유발할 수 있는 비관적 락 대신, NONE → PENDING → COMPLETED로 이어지는 상태 머신과 DB 레벨의 조건부 UPDATE(CAS 유사 방식)를 활용했습니다.

  • 판매자가 채팅에서 안전결제를 요청합니다.
  • WHERE safe_payment_st = 'NONE'인 경우에만 PENDING 상태로 업데이트합니다. 여러 구매자가 동시에 접근해도 단 하나의 UPDATE 쿼리만 성공하며, 실패한 요청은 "이미 결제 진행 중"이라는 응답을 받게 됩니다.
  • 성공 시 pending_buyer_seq와 5분의 만료 시간을 함께 저장하고, 결제 완료 시점에도 PENDING + pending_buyer_seq 일치 조건을 확인하여 COMPLETED로 처리합니다.

2. 정산은 비관적 락(FOR UPDATE)으로 강하게 보호

정산 과정은 결제 시작과 달리 금액 계산, 판매자 검증, 구매확정 여부 확인, 정산 데이터(settlement) 생성, 거래 상태 변경 등 여러 작업이 하나의 원자적 흐름으로 묶여야 하는 금융 트랜잭션입니다.

  • 상태 확인부터 데이터 생성 및 변경까지의 모든 과정에서 데이터 무결성을 완벽히 보장하기 위해 비관적 락(Pessimistic Lock)을 적용했습니다.
  • MyBatis Mapper에서 거래 레코드를 조회할 때 FOR UPDATE 구문을 사용해 대상 row를 선점하고 처리를 진행하도록 구현했습니다.
  • 결과적으로 결제 요청은 조건부 UPDATE로 빠르게 통과시키고, 복잡한 검증이 얽힌 정산 로직은 비관적 락으로 정확성을 최우선시하여 전체 시스템의 효율과 안정성의 밸런스를 맞췄습니다.

성능 개선

1. 중고책 거래 관련 인덱스 설정

  • idx_trade_list_filtered : 메인 거래 목록/필터/정렬 최적화
    적용 컬럼: (del_dtm, category_seq, sale_st, crt_dtm DESC)
  • idx_chat_msg_room_time : 채팅방 메시지 시간순 조회 최적화
    적용 컬럼: (chat_room_seq, sent_dtm)
  • idx_chat_msg_unread : 읽지 않은 메시지 조회/읽음 처리 최적화
    적용 컬럼: (chat_room_seq, read_yn, sender_seq)
  • idx_trade_payment_expiry : 만료된 안전결제 스케줄러 Full Scan 방지
    적용 컬럼: (safe_payment_st, safe_payment_expire_dtm)
  • idx_trade_auto_confirm : 자동 구매확정 대상 조회 최적화
    적용 컬럼: (confirm_purchase, sale_st, del_dtm, sale_st_dtm)

중고책 거래 파이프라인에서 조회 빈도가 높은 거래 목록, 채팅 메시지, 안전결제 스케줄러 쿼리를 중심으로 복합 인덱스를 설계했습니다.

  • 거래 목록은 삭제 여부, 카테고리, 판매 상태, 최신순 정렬 조건을 기준으로 조회되기 때문에 (del_dtm, category_seq, sale_st, crt_dtm DESC) 인덱스를 적용했습니다.
  • 또한 채팅방 메시지 조회와 읽음 처리는 각각 (chat_room_seq, sent_dtm), (chat_room_seq, read_yn, sender_seq) 인덱스를 적용하여 반복 조회 비용을 줄였습니다.
  • 안전결제 만료 및 자동 구매확정처럼 주기적으로 실행되는 스케줄러 쿼리는 상태값과 기준 시간을 함께 사용하는 복합 인덱스를 적용하여 Full Scan을 방지했습니다.

2. Redis 캐시 설정

메인 화면에서는 카테고리 필터, 판매 상태, 검색어, 정렬 조건, 페이지 조합이 동일한 반복 요청이 자주 발생할 수 있습니다.
동일 조건의 목록 조회가 매번 DB로 전달되면 불필요한 조회 부하가 발생하므로, 전체 거래 목록과 전체 거래 개수 등을 Redis에 캐싱했습니다.

3. Redis Pub/Sub 도입 배경 - 멀티 서버 환경에서의 실시간 채팅 문제

Auto Scaling 환경에서 WAS 인스턴스가 2대로 늘어난 뒤 1:1 채팅 메시지가 실시간으로 전달되지 않는 문제가 발생했습니다. 원인은 WebSocket 세션이 각 서버 메모리에 로컬로 유지되어, 한 서버에서 전송한 STOMP 메시지가 다른 서버에 연결된 사용자에게 전달되지 않는 구조였습니다.

이를 해결하기 위해 Redis Pub/Sub을 도입했습니다. 채팅 메시지를 Redis 채널에 publish하고 모든 WAS 인스턴스가 해당 채널을 subscribe하도록 구성하여, 어느 서버에서 메시지가 발생하더라도 각 서버가 자신에게 연결된 클라이언트에게 메시지를 전달할 수 있도록 개선했습니다.

회고 및 배운 점

  • Auto Scaling은 현재 규모에서는 과한 선택일 수 있었고, 트래픽 규모에 맞는 아키텍처 선택의 중요성을 배웠습니다.
  • Redis 캐시는 변경이 잦은 상세 조회보다 반복 조회가 많은 목록성 데이터에 적합하다는 점을 경험했습니다.
