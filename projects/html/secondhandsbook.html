Toss 안전 결제 실패 시

안전결제 과정에서는 결제 실패, 사용자 취소, 페이지 이탈, 결제 시간 초과와 같은 예외 상황이 발생할 수 있습니다. 이때 거래 상태가 PENDING 상태로 남아 있으면 다른 구매자가 해당 상품을 결제할 수 없고, 판매글이 잠긴 상태로 유지되는 문제가 발생할 수 있습니다.

이를 방지하기 위해 결제 실패 및 이탈 상황을 하나의 공통 복구 API인 POST /payments/failure로 처리하도록 설계했습니다. Toss 결제 실패, 사용자의 결제창 닫기, 안전결제 페이지 이탈, 5분 결제 타임아웃이 발생하면 모두 동일한 API를 호출하도록 구성했습니다.

  • API에서는 trade_seq가 일치하는지, 거래 상태가 PENDING인지, pending_buyer_seq가 현재 로그인한 구매자인지 검증한 뒤 상태를 복구합니다.
  • 복구가 정상 처리되면 safe_payment_st는 NONE으로 변경하고, pending_buyer_seq와 safe_payment_expire_dtm은 NULL로 초기화합니다.
  • sale_st는 SALE 상태를 유지하고, member_buyer_seq, confirm_purchase, settlement_st처럼 실제 거래 완료 이후 변경되어야 하는 값은 수정하지 않습니다.

즉, 결제 실패나 중도 이탈이 발생해도 거래는 다시 판매중 + 안전결제 잠금 해제 상태로 복구됩니다. 또한 사용자가 브라우저를 닫거나 네트워크 문제로 복구 API가 호출되지 않는 경우를 대비해, 만료 시간이 지난 PENDING 거래를 스케줄러가 보조적으로 정리하도록 설계했습니다. 이를 통해 클라이언트 이벤트에만 의존하지 않고 서버 측에서도 결제 잠금 상태가 장시간 유지되지 않도록 안정성을 보완했습니다.

문제와 해결: 상태 선점과 금융성 후처리의 동시성 제어 전략 분리

안전결제 요청 단계는 외부 결제 승인 전, 특정 구매자에게 결제 진행 권한을 짧게 선점시키는 흐름입니다. 따라서 비관적 락을 길게 유지하지 않고, safe_payment_st = 'NONE' 조건을 가진 UPDATE로 NONE → PENDING 상태 전이를 원자적으로 처리했습니다. 여러 요청이 동시에 들어와도 DB에서 단 하나의 UPDATE만 성공하므로 결제 진행자는 한 명으로 제한됩니다.

반면 정산 신청은 이미 결제가 완료되고 구매확정까지 끝난 거래에 대해, 검증 결과를 바탕으로 settlement row를 생성하고 거래의 settlement_st를 REQUESTED로 변경하는 후처리 트랜잭션입니다. 이 과정에서는 같은 거래에 대한 중복 정산 신청을 막아야 하므로, 거래 row를 SELECT ... FOR UPDATE로 잠근 뒤 검증, 수수료 계산, 정산 INSERT, 거래 상태 변경을 하나의 트랜잭션으로 처리했습니다.

임계 구간의 성격에 따라 전략을 나눴습니다.
결제 진행자 선점은 조건부 UPDATE로, 정산 신청처럼 읽기-검증-생성이 묶인 흐름은 FOR UPDATE로 제어했습니다.

성능 개선

1. 중고책 거래 관련 인덱스 설정

  • idx_trade_list_filtered : 메인 거래 목록/필터/정렬 최적화
    적용 컬럼: (del_dtm, category_seq, sale_st, crt_dtm DESC)
  • idx_chat_msg_room_time : 채팅방 메시지 시간순 조회 최적화
    적용 컬럼: (chat_room_seq, sent_dtm)
  • idx_chat_msg_unread : 읽지 않은 메시지 조회/읽음 처리 최적화
    적용 컬럼: (chat_room_seq, read_yn, sender_seq)
  • idx_trade_payment_expiry : 만료된 안전결제 스케줄러 Full Scan 방지
    적용 컬럼: (safe_payment_st, safe_payment_expire_dtm)
  • idx_trade_auto_confirm : 자동 구매확정 대상 조회 최적화
    적용 컬럼: (confirm_purchase, sale_st, del_dtm, sale_st_dtm)

중고책 거래 파이프라인에서 조회 빈도가 높은 거래 목록, 채팅 메시지, 안전결제 스케줄러 쿼리를 중심으로 복합 인덱스를 설계했습니다.

  • 거래 목록은 삭제 여부, 카테고리, 판매 상태, 최신순 정렬 조건을 기준으로 조회되기 때문에 (del_dtm, category_seq, sale_st, crt_dtm DESC) 인덱스를 적용했습니다.
  • 또한 채팅방 메시지 조회와 읽음 처리는 각각 (chat_room_seq, sent_dtm), (chat_room_seq, read_yn, sender_seq) 인덱스를 적용하여 반복 조회 비용을 줄였습니다.
  • 안전결제 만료 및 자동 구매확정처럼 주기적으로 실행되는 스케줄러 쿼리는 상태값과 기준 시간을 함께 사용하는 복합 인덱스를 적용하여 Full Scan을 방지했습니다.

2. Redis 캐시 설정

메인 화면에서는 카테고리 필터, 판매 상태, 검색어, 정렬 조건, 페이지 조합이 동일한 반복 요청이 자주 발생할 수 있습니다.
동일 조건의 목록 조회가 매번 DB로 전달되면 불필요한 조회 부하가 발생하므로, 전체 거래 목록과 전체 거래 개수 등을 Redis에 캐싱했습니다.

3. Redis Pub/Sub 도입 배경 - 멀티 서버 환경에서의 실시간 채팅 문제

Auto Scaling 환경에서 WAS 인스턴스가 2대로 늘어난 뒤 1:1 채팅 메시지가 실시간으로 전달되지 않는 문제가 발생했습니다. 원인은 WebSocket 세션이 각 서버 메모리에 로컬로 유지되어, 한 서버에서 전송한 STOMP 메시지가 다른 서버에 연결된 사용자에게 전달되지 않는 구조였습니다.

이를 해결하기 위해 Redis Pub/Sub을 도입했습니다. 채팅 메시지를 Redis 채널에 publish하고 모든 WAS 인스턴스가 해당 채널을 subscribe하도록 구성하여, 어느 서버에서 메시지가 발생하더라도 각 서버가 자신에게 연결된 클라이언트에게 메시지를 전달할 수 있도록 개선했습니다.

회고 및 배운 점

  • Auto Scaling은 현재 규모에서는 과한 선택일 수 있었고, 트래픽 규모에 맞는 아키텍처 선택의 중요성을 배웠습니다.
  • Redis 캐시는 변경이 잦은 상세 조회보다 반복 조회가 많은 목록성 데이터에 적합하다는 점을 경험했습니다.
