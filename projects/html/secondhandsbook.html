기술적 선택 근거

메인 화면에서 판매 상태, 카테고리, 검색 조건 등 다양한 필터 기반 동적 조회가 빈번하게 발생했기 때문에,
복잡한 동적 SQL을 유연하게 관리하고 쿼리 제어를 세밀하게 수행하기 위해 MyBatis를 선택했습니다.

프로젝트가 JSP 기반 SSR(Server Side Rendering) 구조였기 때문에
클라이언트 측 토큰 저장 방식보다 서버에서 사용자 인증 상태를 직접 관리하는 Session & Cookie 기반 인증 방식이 구조적으로 적합하다고 판단했습니다.

트래픽 증가 시 단일 서버 환경에서는 서버 다운 위험이 존재했기 때문에,
AWS ELB와 Auto Scaling을 활용하여 동일 스펙의 EC2 인스턴스가 자동으로 확장되는 멀티 서버 아키텍처를 구성했습니다.
이를 통해 특정 서버에 트래픽이 집중되는 문제를 완화하고, 서버 장애 발생 시 가용성을 확보하여 서비스 안정성을 향상시킬 수 있었습니다.

순수 WebSocket만으로도 실시간 채팅 구현은 가능했지만,
향후 멀티 서버 환경에서 세션 및 메시지 관리를 보다 유연하게 처리하기 위해 STOMP 프로토콜을 도입했습니다.
이를 통해 채팅 메시지 라우팅 구조를 단순화하고 Publish/Subscribe 기반 메시징 처리를 가능하게 하여 서버 확장 시 구조 변경을 최소화했습니다.

멀티 서버 환경에서는 서버마다 메모리 영역이 분리되어 세션 및 실시간 데이터 동기화가 필요했기에 Redis를 도입했습니다.
회원 로그인 시 Session 데이터를 Redis에 저장하여 서버 간 동일한 인증 상태를 유지하고,
1:1 채팅 시 Redis Pub/Sub 기능을 사용해 서버 간 채팅 메시지를 동기화했습니다.
또한 도서 카테고리 등 자주 변경되지 않는 데이터를 캐싱하여 DB 조회 횟수를 줄이고 응답 속도를 개선했습니다.

중고책 이미지 파일 저장을 위해 S3를 사용하고,
정적 이미지 응답 속도 개선 및 트래픽 분산을 위해 CloudFront CDN을 적용했습니다.
이를 통해 서버와 이미지 저장소를 분리하여 정적 리소스 응답 속도를 향상시키고 서버 부하를 감소시키는 효과를 얻었습니다.

AWS 인프라 리소스 상태 및 서버 로그 모니터링을 위해 CloudWatch를 사용했습니다.
이를 통해 CPU 및 메모리 사용량을 모니터링하고, 서버 상태 및 장애 로그를 확인하며 트래픽 증가 상황에 대응하는 등 운영 환경의 안정성을 효율적으로 관리했습니다.

성능 개선

1. 중고책 거래 관련 인덱스 설정

  • idx_trade_list_filtered : 메인 거래 목록/필터/정렬 최적화
    적용 컬럼: (del_dtm, category_seq, sale_st, crt_dtm DESC)
  • idx_chat_msg_room_time : 채팅방 메시지 시간순 조회 최적화
    적용 컬럼: (chat_room_seq, sent_dtm)
  • idx_chat_msg_unread : 읽지 않은 메시지 조회/읽음 처리 최적화
    적용 컬럼: (chat_room_seq, read_yn, sender_seq)
  • idx_trade_payment_expiry : 만료된 안전결제 스케줄러 Full Scan 방지
    적용 컬럼: (safe_payment_st, safe_payment_expire_dtm)
  • idx_trade_auto_confirm : 자동 구매확정 대상 조회 최적화
    적용 컬럼: (confirm_purchase, sale_st, del_dtm, sale_st_dtm)

중고책 거래 파이프라인에서 조회 빈도가 높은 거래 목록, 채팅 메시지, 안전결제 스케줄러 쿼리를 중심으로 복합 인덱스를 설계했습니다.

  • 거래 목록은 삭제 여부, 카테고리, 판매 상태, 최신순 정렬 조건을 기준으로 조회되기 때문에 (del_dtm, category_seq, sale_st, crt_dtm DESC) 인덱스를 적용했습니다.
  • 또한 채팅방 메시지 조회와 읽음 처리는 각각 (chat_room_seq, sent_dtm), (chat_room_seq, read_yn, sender_seq) 인덱스를 적용하여 반복 조회 비용을 줄였습니다.
  • 안전결제 만료 및 자동 구매확정처럼 주기적으로 실행되는 스케줄러 쿼리는 상태값과 기준 시간을 함께 사용하는 복합 인덱스를 적용하여 Full Scan을 방지했습니다.

2. Redis 캐시 설정

메인 화면에서는 카테고리 필터, 판매 상태, 검색어, 정렬 조건, 페이지 조합이 동일한 반복 요청이 자주 발생할 수 있습니다.
동일 조건의 목록 조회가 매번 DB로 전달되면 불필요한 조회 부하가 발생하므로, 전체 거래 목록과 전체 거래 개수 등을 Redis에 캐싱했습니다.

[ 캐싱 동작 조건 ]
  • Key : tradeList
    - 같은 필터/정렬/페이지 조합으로 거래 목록을 다시 조회할 때 사용
    - 캐시 키 구성: page, category_seq, search_word, sort, sale_st, book_st
    - TTL: 5분
  • Key : tradeCount
    - 메인 화면 페이징 계산 시 같은 조건의 전체 개수를 다시 조회할 때 사용
    - 캐시 키 구성: category_seq, search_word, sale_st, book_st
    - TTL: 5분
  • Key : categoryList
    - 관리자 페이지에서 추가되며, 변경 빈도가 거의 없는 판매글 카테고리 목록
    - TTL: 24시간
[ 캐시 무효화 (Cache Evict) 조건 ]
  • tradeList / tradeCount 무효화
    • 판매글 등록 / 수정 / 삭제
    • 찜 추가 / 취소
    • 판매 상태 변경 (SALE, RESERVED, SOLD) 및 수동 판매완료 처리
    • 15일 경과 후 자동 구매확정 처리 / Toss 안전결제 완료 처리
    • 회원 탈퇴 시 판매글 일괄 삭제
  • categoryList 무효화
    • 관리자 페이지에서 관리자가 카테고리 추가, 삭제, 수정 시 동작

3. 안전결제 전달 및 완료 처리 시 비인가 요청 차단

안전결제 요청과 완료 처리를 모두 조건부 UPDATE로 설계해, 애플리케이션 검증뿐 아니라 DB 레벨에서도 안전결제를 선점한 구매자만 결제를 진행할 수 있도록 했습니다.

WHERE trade_seq = ?
  AND safe_payment_st = 'PENDING'
  AND pending_buyer_seq = ?

조건부 UPDATE를 통해 안전결제를 선점한 사용자만 결제를 완료할 수 있도록 처리했습니다.

4. Redis Pub/Sub 도입 배경 - 멀티 서버 환경에서의 실시간 채팅 문제

Auto Scaling 환경에서 WAS 인스턴스가 2대로 늘어난 뒤 1:1 채팅 메시지가 실시간으로 전달되지 않는 문제가 발생했습니다. 원인은 WebSocket 세션이 각 서버 메모리에 로컬로 유지되어, 한 서버에서 전송한 STOMP 메시지가 다른 서버에 연결된 사용자에게 전달되지 않는 구조였습니다.

이를 해결하기 위해 Redis Pub/Sub을 도입했습니다. 채팅 메시지를 Redis 채널에 publish하고 모든 WAS 인스턴스가 해당 채널을 subscribe하도록 구성하여, 어느 서버에서 메시지가 발생하더라도 각 서버가 자신에게 연결된 클라이언트에게 메시지를 전달할 수 있도록 개선했습니다.

회고 및 배운 점

Auto Scaling 적용에 대한 고민

초기에는 Auto Scaling 기반 멀티 서버 구조를 적용했지만, 현재 프로젝트 규모에서는 다소 과한 구조였을 수 있다고 느꼈습니다.

이를 통해 단순한 확장성보다 서비스 규모와 트래픽 패턴에 맞는 아키텍처 선택이 중요하다는 점을 배웠습니다.

Redis 캐싱 전략

초기에는 판매글 상세 조회에도 Redis Cache를 적용했습니다.
하지만 판매글 상세 데이터는:

  • 조회수 증가
  • 판매 상태 변경
  • 게시글 수정

등으로 인해 Cache Evict가 자주 발생했고,
결과적으로 조회 대비 캐시 유지 효율이 높지 않았습니다.

이후에는:

  • 반복 조회 비율이 높은 목록성 데이터 위주로 캐싱을 유지하고
  • 변경이 잦은 상세 데이터는 DB에서 직접 조회

하도록 전략을 수정했습니다.

이를 통해 캐싱은 단순히 “빠르게 만들기 위한 기술”이 아니라,
조회 대비 Update/Delete 비율과 데이터 변경 주기를 함께 고려하여 적용해야 한다는 점을 이해하게 되었습니다.

AWS 클라우드 환경 운영 경험

AWS 기반 멀티 서버 환경을 직접 구성하며 로드밸런싱, 세션 공유, CDN 기반 정적 리소스 분리, 모니터링 환경 구축 등을 경험했습니다.

향후 MSA 확장 가능성에 대한 고민

프로젝트를 진행하며 도메인 규모가 커질 경우 서비스 단위 분리 필요성을 느꼈습니다.

향후에는 거래/결제와 커뮤니티 기능을 분리하여 독립 배포 및 확장 가능한 구조로 개선할 수 있다고 생각했습니다.

향후 정산 자동화 및 배치 처리 도입에 대한 고민

현재 시스템에서는 구매 확정된 거래에 대해 관리자가 직접 판매자의 계좌로 정산 금액을 송금하는 수동 방식으로 운영되고 있습니다.
하지만 서비스 규모가 커질수록 이러한 방식은 관리자의 업무 부담을 가중시키고 송금 지연 및 휴먼 에러를 유발할 수 있다고 느꼈습니다.

이를 개선하기 위해 향후에는 정산 프로세스를 자동화해야겠다는 필요성을 깨달았습니다.

구상 중인 개선 흐름은 다음과 같습니다:

  • 관리자가 서비스 내부 정산 Pool에 일정 금액을 사전 충전
  • 매일 특정 시간에 배치 프로세스가 실행되어 당일 구매 확정된 거래 목록을 일괄 조회
  • 충전금에서 각 판매자에게 지급할 정산금을 자동으로 차감 및 이체 처리

이러한 과정을 통해, 단순히 기능을 동작하게 하는 것을 넘어 대량의 트랜잭션을 안정적이고 효율적으로 처리하는 배치 처리 기술의 중요성을 생각해 볼 수 있었습니다.
